# ④ 운영 비용 모델 — Databricks Apps 중심

> **목적**: Databricks Apps를 운영 Runtime으로 쓸 때 발생하는 비용의 구조와 규모를 확정 가능한 형태로 정리하고, 그 결과를 런타임 판정 기준·파이프라인·앱마켓 설계에 되돌린다.
> **작성일**: 2026-09-12
> **선행 문서**: `databricks-apps-reference.md` §3, `03-runtime-decision-and-architecture.md` §3, `02-cicd-pipeline-design.md` §9-3
> **배경**: 선행 문서들은 "0.5 DBU/h, 실행 중 상시 과금"을 사실로만 기록하고 **총량을 계산하지 않았으며, 앱 컨테이너 단가만 보고 있었다.** 실제 청구서에서 앱 컨테이너는 가장 작은 항목이다.

---

## 0. 요약

| 결론 | 근거 |
|---|---|
| **Databricks Apps에는 auto-stop이 없다.** 유휴 정지를 플랫폼이 직접 구현하지 않으면 구조적으로 70~85%가 낭비된다 | §1 |
| **비용의 지배 항목은 앱 컨테이너가 아니라 뒤에 붙는 SQL Warehouse다.** 서버리스 Small이 앱 Medium의 24배 | §2-2 |
| **앱 전용 웨어하우스는 성립하지 않는다.** 100개 앱에 전용 웨어하우스를 붙이면 연 30억원대. 그런데 지금 설계에 이를 금지하는 규칙이 없다 | §2-2 |
| **상시 구동 앱 100개 = 연 3~6억원 규모의 의사결정** (웨어하우스 제외) | §3 |
| dev/staging/prod 3환경이면 **앱 인스턴스는 앱 수의 3배** | §4 |
| `03` §3의 3층 기본값은 **무조건이 아니라 조건부**여야 한다 | §5-a |
| 100개 한도는 용량 제약이 아니라 **예산 가드레일**로 읽어야 한다 | §5-b |
| OBO 기본 정책에는 문서화되지 않은 **비용 상충**이 있다. 포기 근거가 아니라 측정 대상 | §5-c |

## 1. 단가 사실관계

### 1-1. 확인된 것

| 항목 | 값 | 등급 |
|---|---|---|
| Apps **Medium** | 최대 2 vCPU / 6 GB / **0.5 DBU/h** | ✅ 공식 |
| Apps **Large** | 최대 4 vCPU / 12 GB / **1 DBU/h** | ✅ 공식 |
| DBU 단가에 기반 컴퓨트(EC2) **포함** | 네트워킹·데이터 전송은 별도 청구 | ✅ Databricks 직원 답변 |
| **Apps에 auto-stop / scale-to-zero 기능이 없다** | SQL Warehouse와 달리 유휴 정지 설정 자체가 존재하지 않음. 시작/정지를 스케줄 잡이나 외부 스케줄러로 직접 호출해야 함 | ⚠️ 커뮤니티·MVP 글. **공식 문서에 해당 설정이 부재하다는 사실이 근거** |
| 서버리스 SQL Warehouse **Small** | **12 DBU/h** | ✅ 공식 |
| SQL Warehouse auto-stop | 기본 10분 / UI 최소 5분 / **API 최소 1분** | ✅ 공식 |

> `databricks-apps-reference.md` §3은 "실행 중인 시간에 대해서만 과금"이라고만 적었다. 이 진술은 사실이지만, **"실행을 언제 멈추는가"에 대한 기능이 플랫폼에 없다**는 점이 빠져 있어 실제로는 상시 과금으로 귀결된다. 해당 절에 이 사실을 보강할 것.

### 1-2. 미확인 — 계산의 유일한 빈칸

**Apps SKU의 $/DBU.** 공식 가격 페이지는 값이 동적 로딩되어 정적 조회로 읽히지 않는다. 커뮤니티 스레드의 "$75/DBU"는 Databricks 전체 DBU 단가 스케일($0.07~$0.70)과 모순되므로 채택하지 않았다.

대신 실측 데이터점이 하나 있다 — **24/7 상시 구동 앱 1개 ≈ $350/월(720h)**. 역산하면 실효 단가는 **$0.5 ~ $1.0/DBU** 구간이다. 본 문서의 모든 금액은 이 밴드로 표기한다.

**확정 방법** — 웹 자료가 아니라 계정에서 직접 읽는다.

```sql
SELECT sku_name, currency_code, usage_unit, pricing.effective_list
FROM system.billing.list_prices
WHERE sku_name ILIKE '%APP%' AND price_end_time IS NULL;
```

> `system.billing.list_prices`는 **list price만** 제공한다. 협상 단가가 있으면 계약서 기준으로 재계산할 것.

### 1-3. 계산 전제

| 전제 | 값 |
|---|---|
| 월 시간 | 730h (24/7) / 220h (평일 9–18시, 22일) |
| Apps 실효 단가 | $0.5 ~ $1.0 / DBU (§1-2) |
| 서버리스 SQL 단가 | $0.70 / DBU (공표 list price 기준) |
| 환율 | 1 USD ≈ 1,400원 **(가정. 확정 시 수정)** |
| 클라우드·리전 | ✅ AWS · ap-northeast-2 (서울). Databricks는 **별도 전용 계정** (`03` 문서 F1·F2) |
| 계약 tier | ✅ **Enterprise** (`03` 문서 F3). 네트워크 정책 사용 가능 — §6-2 공용 웨어하우스 강제와 함께 이그레스 통제도 가능 |

## 2. 비용은 3층이다

선행 문서들이 보고 있던 것은 1층뿐이다.

### 2-1. 1층 — 앱 컨테이너

| 구동 패턴 | DBU/월 | 추정 비용/월 |
|---|---|---|
| Medium 24/7 | 365 | $180 ~ $350 |
| Large 24/7 | 730 | $365 ~ $700 |
| Medium 평일 9–18시 (220h) | 110 | $55 ~ $105 |

**auto-stop 부재의 무게가 여기서 나온다.** 사내 업무앱의 실사용은 통상 하루 몇 시간이므로, 아무 조치가 없으면 **구조적으로 70~85%가 낭비**된다. 인용 사례에는 테스트 앱 하나가 69일간 유휴 방치되어 약 $800이 소진된 건이 있다.

**앱마켓은 정의상 롱테일 앱이 많은 카탈로그다.** 즉 이 실패 모드가 예외가 아니라 기본값이 된다.

평일 업무시간으로 제한하면 **약 70% 절감** (110/365). 인용 사례의 실측치는 76% (주 50시간 vs 168시간).

### 2-2. 2층 — SQL Warehouse (선행 문서에 없음. 실제 지배 항목)

UC 데이터를 쓰는 앱은 뒤에 웨어하우스가 돌아야 한다. 서버리스 Small = **12 DBU/h**, 앱 Medium의 **24배**다.

| 구성 | DBU/월 | 추정 비용/월 | 연 환산(원, 가정 환율) |
|---|---|---|---|
| 공용 Small 1대, 평일 업무시간 warm (220h) | 2,640 | 약 $1,850 | 약 0.31억 |
| 공용 Small 1대, 사실상 24/7 warm | 8,760 | 약 $6,130 | 약 1.03억 |
| **앱마다 전용 웨어하우스 (100개, 220h)** | 264,000 | **약 $184,800** | **약 31억** |

**마지막 행이 요점이다. 앱 전용 웨어하우스는 성립하지 않는다.** 그런데 지금 설계 어디에도 이를 금지하는 규칙이 없어, 스캐폴드를 받은 팀이 각자 웨어하우스를 만드는 것이 자연스러운 기본 동작이 된다. → §6-2

**auto-stop 5분이 앱마켓에서는 거의 작동하지 않는다.** 앱 수십 개가 하루 종일 산발적으로 쿼리를 던지면 유휴 5분이 채워지지 않으므로, 공용 웨어하우스는 실질적으로 업무시간 내내 warm 상태로 유지된다. 즉 위 표의 220h는 낙관이 아니라 현실적 하한이다.

또한 Small의 12 DBU/h는 **바닥값**이다. 동시성이 올라가면 클러스터가 오토스케일되어 배수로 증가한다.

### 2-3. 3층 — Agent App 변동비 (선행 문서에 없음)

- 모델 서빙: 토큰 과금 또는 프로비저닝 스루풋(DBU-시간)
- Genie space 질의, 벡터 검색

Agent App은 **사용자 1회 대화가 여러 번의 LLM 호출 + 여러 번의 웨어하우스 쿼리로 번진다.** 따라서 사용자당 변동비가 일반 Web App과 자릿수가 다르다.

`03` §6 메타데이터에 `cost_monthly_krw` 필드는 있으나, Agent App의 변동비를 어떤 단위로 귀속시킬지가 정의되지 않았다. → §6-4

## 3. 규모 시나리오

앱 컨테이너만, 전부 Medium 상시 구동 기준 (**웨어하우스 제외**).

| 앱 수 | DBU/월 | 추정/년 | 원화(1,400원 가정) |
|---|---|---|---|
| 10 | 3,650 | $22k ~ $44k | 0.3억 ~ 0.6억 |
| 50 | 18,250 | $110k ~ $219k | 1.5억 ~ 3.1억 |
| **100 (워크스페이스 한도)** | 36,500 | $219k ~ $438k | **3.1억 ~ 6.1억** |
| 300 (3 워크스페이스) | 109,500 | $657k ~ $1.3M | 9.2억 ~ 18.4억 |

여기에 공용 웨어하우스(업무시간 warm) 1~3대를 더하면 연 0.3억~0.9억이 추가된다.

## 4. 환경 배수

`02` §3은 dev / staging / prod 3환경이다. Databricks Apps는 **환경별로 별도 앱 인스턴스**이므로,

> **AX App 100개 = 앱 인스턴스 300개**

dev/staging에 정지 정책이 없으면 §3 표의 **3배**가 된다. → §6-5

## 5. 설계에 되돌리는 결론

### 5-a. `03` §3의 3층 기본값은 조건부여야 한다

"둘 다 NO → Databricks Apps (1안 기본값)"의 실제 비교 대상은 "DBU 단가 vs 클라우드 VM 단가"가 아니다. Private Cloud(VKS)는 **이미 구축된 온프렘 하드웨어**이므로 2 vCPU 파드 하나의 한계비용은 0에 가깝다. 비교는 **연 수억원 vs 거의 0**이다.

**기본값을 뒤집으라는 뜻은 아니다.** 1단계(앱 10개 내외)에서 1안은 타당하고, Q1의 물리적 제약(`03` §3)과 Q5의 통제 이점은 그대로 유효하다. 다만 기본값을 조건부로 만들어야 한다.

> **수정 문구(안)**: "유휴 정지 정책(§6-1)과 공용 웨어하우스 규칙(§6-2)이 플랫폼에 구현되어 있는 동안에만 Databricks Apps를 기본값으로 한다."

미구현 상태에서 앱 수가 늘어나면 비용이 앱 수에 선형으로 따라 올라간다.

### 5-b. 100개 한도는 예산 가드레일이다

`databricks-apps-reference.md` §3과 `03` Q4는 100개 한도를 "워크스페이스 증설로 푸는 용량 문제"로 다룬다. 비용 관점에서는 반대로 읽어야 한다.

- 한 워크스페이스를 상시 구동 앱 100개로 채우는 것 = **연 3~6억원 규모의 의사결정**
- 워크스페이스 증설 = 그 제동장치를 해제하는 행위

→ **증설은 용량 판단이 아니라 예산 승인 항목으로 절차화할 것.**

### 5-c. OBO 기본 정책의 비용 상충

문서 세 건이 일관되게 OBO를 기본으로 못 박고 있고, 그 판단 자체는 타당하다(데이터 거버넌스 책임을 앱 코드에서 플랫폼으로 이전). 다만 비용 측면이 비어 있다.

UC 행 필터·컬럼 마스킹이 걸린 테이블에서는 쿼리 엔진이 **최적화와 정보 유출 방지 사이에서 항상 안전한 선택**을 한다. 필터 푸시다운이 제한되고 결과 재사용 조건이 까다로워진다. 결과적으로 웨어하우스 비용이 "서로 다른 쿼리 수"가 아니라 **사용자 수에 가깝게** 증가한다.

> ⚠️ 이것은 **OBO를 포기할 근거가 아니다.** 보안 통제를 사는 대가이고, 그 대가의 크기를 파일럿에서 측정해야 한다는 뜻이다. 상충의 정확한 크기는 워크로드 의존이므로 §7의 실측 항목으로 넘긴다.

### 5-d. `03` Q8의 위치가 틀렸다

Q8은 현재 "상시 고트래픽? → 비용 비교 후 결정"으로 3층 맨 끝에 있다. 그러나 비용은 트래픽이 아니라 **앱 개수 × 구동 시간**에서 발생한다. **저트래픽 앱 100개가 고트래픽 앱 1개보다 훨씬 비싸다.**

> **수정 문구(안)**: Q8을 **"업무시간 외 정지가 가능한가"** 로 재정의한다. 정지 불가(24/7 SLA 요구)인 앱이 비용 게이트 대상이다.

이는 앞서 지적된 "Q8은 비용이 아니라 용량 상한 문제"(Large 4 vCPU 천장 + 수평 확장 Beta)와 같은 결론으로 수렴한다. 즉 **Q8은 두 가지 이유로 3층에서 올라와야 한다.**

## 6. 설계에 추가할 통제 규칙

### 6-1. 유휴 정지를 플랫폼 의무로 만든다 ⭐

Apps에 auto-stop이 없으므로 다음을 **스캐폴드와 플랫폼 운영에 기본 탑재**한다.

- Apps REST API를 호출하는 스케줄 잡(시작/정지) 또는 유휴 감지 후 정지
- 기준: 평일 09–18시 구동 (약 70% 절감)
- **개별 팀에 맡기지 않는다.** 맡기면 반드시 방치된다 (§2-1의 69일 사례)

### 6-2. 공용 SQL Warehouse 강제, 앱 전용 웨어하우스 금지 ⭐

OBO가 사용자 신원을 그대로 전달하므로 웨어하우스를 공유해도 권한 분리는 유지된다.

**가장 싼 강제 지점은 `02` §6-1의 `validate` 스테이지다.** 앱 설정이 승인되지 않은 전용 웨어하우스를 참조하면 파이프라인을 실패시킨다. (동 절의 "SP 모드면 승인 레이블 없이 실패" 규칙과 같은 위치·같은 방식)

### 6-3. 마켓 UI에 "정지됨 → 시작"을 1급 개념으로 넣는다

`03` §6의 `deployment.status`에 `stopped`는 있으나 다음이 없다.

- 수명주기 정책 (누가 언제 정지/기동하는가)
- 과금 주체 (소유 조직)
- **콜드 스타트 대기 UX** — 정지 정책을 도입하면 이것이 사용자 경험의 일부가 된다

### 6-4. 앱별 비용 귀속(showback)

`system.billing.usage`에 Apps SKU와 `created_by`가 기록되므로 앱 단위 집계가 가능하다. 소유 조직에 월 비용을 노출하는 것만으로 방치 앱이 줄어든다.

→ `03` §6의 `cost_monthly_krw`와 `deprecation`을 연결하는 자연스러운 지점. Agent App은 §2-3의 변동비 항목을 별도 필드로 분리할 것.

### 6-5. dev/staging은 더 강하게 정지한다

필요할 때만 기동, 또는 환경 공유. 방치하면 총비용이 3배(§4).

## 7. 파일럿에서 실측할 것

추정으로 남기지 않는다.

| # | 측정 항목 | 방법 | 확정되는 것 |
|---|---|---|---|
| 1 | **Apps SKU의 실제 $/DBU** | §1-2 `list_prices` 쿼리 | §3 표의 밴드가 단일값으로 확정 |
| 2 | **과금 최소 단위** | 초/분 단위인지, 시작 시 최소 과금이 있는지 | 온디맨드 시작 모델의 타당성 |
| 3 | **콜드 스타트 시간** | 정지된 앱 시작 → 서빙까지 | 30초면 온디맨드 성립, 3분이면 마켓 UX 재설계 |
| 4 | 시작 시 의존성 재설치 여부 | 정지→시작 로그 관찰 | 3번의 원인. 의존성 해석 시점 이슈와 연동 |
| 5 | **OBO + 행·열 보안 쿼리의 웨어하우스 DBU 소모** | 동일 쿼리를 마스킹 없는 테이블과 비교 | §5-c 상충의 크기 |
| 6 | 동시 사용자 50명 시 Medium 1개의 거동 | 부하 테스트 | 용량 천장 (Large도 4 vCPU) |

> 3번과 4번은 §6-1 유휴 정지 정책의 실행 가능성을 직접 결정한다. **정지 정책 도입 전에 측정할 것.**
