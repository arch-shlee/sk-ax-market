# AXM-0004: 런타임 판정 Q1 재정의 — 물리적 제약에서 보안 승인으로

- **상태**: Accepted
- **일자**: 2026-09-12
- **결정자**: 아키텍처
- **관련 문서**: `03` §3 Q1, `05` §3, `databricks-apps-reference.md` §7
- **대체 대상**: 종전 가정 A1 ("서버리스 → 온프렘 직접 아웃바운드 불가")

## 맥락

판정 트리 1층의 Q1은 원래 이랬다.

> **Q1. 사내 시스템 직접 연동 필요? → YES면 Private Cloud 확정**

근거는 "NCC/PrivateLink는 클라우드 사업자 인프라 기반이라 온프렘으로 확장되지 않는다"였고, 출처는 **Databricks 커뮤니티 답변**이었다. 이것이 **판정 트리의 무게중심**이자 "1안 = Databricks Apps 우선" 방침의 명분을 지탱하는 축이었다.

그런데 두 가지 사실이 확인되면서 이 근거가 무너졌다 — 계약이 **Enterprise tier**이고(`AXM-0002`), 온프렘 ↔ AWS가 **DX·TGW로 이미 연결되어 라우팅까지 구성**되어 있다.

## 결정

> Q1을 **"사내 시스템을 내부 NLB 뒤에 노출할 수 없는가?(또는 보안 승인 불가)"** 로 재정의한다. 물리적 제약이 아니라 **조직의 승인 문제**로 다룬다.

성립하는 경로:

```
Databricks App (서버리스, Databricks 계정)
   → NCC 사설 엔드포인트 (PrivateLink)
   → 우리 VPC의 내부 NLB   ← VPC 엔드포인트 서비스로 노출
   → NLB 타깃 → TGW → Direct Connect
   → 온프렘 MES / SRM / ERP / Wehub / CRM
```

## 근거

Databricks **Apps 네트워킹 공식 문서**에 명시되어 있다.

> "To restrict egress to private destinations such as an S3 bucket or **a network load balancer (NLB)**, configure PrivateLink connections as part of your NCC setup."

종전 기술이 절반만 맞았던 것이다. PrivateLink가 온프렘까지 직접 가지 않는 것은 사실이나, **우리 VPC를 중계점으로 두면 나머지 구간은 이미 깔린 DX가 처리한다.** 커뮤니티 답변이 제시했던 "스테이징 계층 방식"보다 훨씬 가볍다.

요구사항: Enterprise tier(충족), 내부 스킴 NLB + VPC 엔드포인트 서비스 + 동일 리전 NCC 객체.
한도: 리전·계정당 NCC 10 / 리전당 사설 엔드포인트 30 / NCC당 워크스페이스 50 / 규칙당 도메인 100.

## 결과

**얻는 것**
- **판정 트리의 무게중심이 1층에서 2층으로 이동한다.** 사내 시스템 연동 앱도 Databricks Apps 후보가 된다
- **1안의 명분이 오히려 강해진다.** 물리적으로 막혀서 갈라지는 것이 아니라 **Q5(UC 행·열 보안 상속)의 통제 이점 때문에 선택하는 것**이 된다. 기획서가 "배경과 명분을 강화해야 한다"고 적은 숙제를 이제 Q1이 아니라 Q5가 받는다

**감수하는 것**
- **Q1의 판정이 기술 판단에서 보안 승인으로 성격이 바뀐다.** 앱마다 승인 리드타임이 생길 수 있다
- 내부 NLB가 **모든 Databricks App의 사내 접근이 통과하는 단일 지점**이 된다. 운영·감사 주체를 정해야 하고, 장애 시 영향 범위가 넓다
- **DNS chasing·redirect 미지원** 제약이 붙는다. 사내 시스템 FQDN이 CNAME 체인이나 GSLB로 해석되면 걸린다

## 검토한 대안

| 대안 | 평가 | 기각 사유 |
|---|---|---|
| 종전대로 유지 (사내 연동 = Private Cloud 확정) | 단순 | 사실과 다르다. 잘못된 근거로 앱을 Private Cloud로 몰면 Q5의 통제 이점을 불필요하게 포기하게 된다 |
| 스테이징 계층 (온프렘 데이터를 클라우드 스토리지로 추출) | 커뮤니티 제시안 | 실시간 연동이 안 된다. 데이터 사본이 늘어 거버넌스 부담 증가 |
| DMZ API 게이트웨이 + NCC 고정 IP allowlist | 성립함 | NCC 사설 엔드포인트가 더 낫다 — 인터넷을 경유하지 않고, 접근 주체를 워크스페이스로 한정할 수 있다. 다만 사내 시스템이 이미 DMZ에 노출되어 있다면 이 경로가 더 쌀 수 있다 |

## 미결 / 후속

- ⚠️ **NLB 타깃을 온프렘 IP로 두는 구성의 검증.** AWS NLB의 IP 타입 타깃은 DX/VPN 너머 주소를 지원하므로 성립할 것으로 보나 **Databricks 문서 범위 밖**이다. 최소 검증: 사내 시스템 1개를 타깃으로 하는 내부 NLB를 만들고 같은 VPC의 EC2에서 도달 확인
- **사내 시스템 노출에 대한 보안팀 승인** — 승인 패키지 초안은 `05` §3-4
- 대상 시스템 FQDN의 해석 방식 확인 (DNS chasing 제약)
- 내부 NLB 배치 계정 결정 (`05` §1-2)
