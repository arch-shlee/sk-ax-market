# AXM-0009: 앱 실행은 리다이렉트 — 마켓 소유 실행 엔드포인트 경유

- **상태**: Accepted
- **일자**: 2026-09-12
- **결정자**: 아키텍처
- **관련 문서**: `03` §5-2, `databricks-apps-reference.md` §4, `05` §2·§5, `AXM-0005`, `AXM-0008`, `AXM-0011`

## 맥락

임직원이 앱마켓에서 "실행"을 눌렀을 때 **그 앱을 쓰는 트래픽이 마켓을 통과하는가.**

- **리다이렉트** — 마켓이 주소만 알려주고 빠진다. 인증·인가는 런타임이 수행
- **프록시** — 마켓이 앞단에서 인증하고 뒤로 중계. 모든 화면·클릭이 마켓을 통과

이 선택이 앱마켓의 **사이징·가용성 등급·장애 범위를 근본적으로 바꾼다.**

그리고 판단에 결정적인 조건이 하나 더 있다. **운영 런타임이 둘이고 물리적 위치가 다르다**(`AXM-0001`, `AXM-0002`).

| | 위치 |
|---|---|
| 앱마켓 | AWS 전용 계정 |
| Databricks Apps | Databricks 계정 (AWS) |
| **Private Cloud (VKS)** | **온프렘** |
| 사용자 (VDI) | **온프렘** |

## 결정

> **리다이렉트.** 단, 마켓이 소유한 **안정된 실행 엔드포인트**를 한 번 거쳐 실제 런타임 주소로 302 한다.

```
사용자 ──▶ market.company.com/launch/ax-app-0001
              │  1) 권한 확인
              │  2) 앱이 정지 상태면 시작 요청 + 대기 화면
              │  3) 현재 런타임의 실제 주소로 302
              ▼
         xxx.databricksapps.com   또는   app.vks.내부도메인
              │
              └─▶ 이후 트래픽은 마켓을 거치지 않는다
```

앱마켓은 권한의 **오케스트레이터**이고, 런타임이 **집행자**다.

| 런타임 | 인증 | 인가 |
|---|---|---|
| Databricks Apps | Databricks 계정 SSO (Cognito OIDC) | `CAN_USE` + OBO → UC 행·열 보안 |
| Private Cloud | Cognito SSO (Ingress forward-auth → `AXM-0011`) | Cognito 그룹 클레임 + Ingress 인가 정책 |

> 2026-09-27 — SSO 중계를 Keycloak에서 Cognito로 교체(`AXM-0014`). 결정 자체는 불변.

## 근거

### 프록시를 기각하는 이유

**1. OBO가 깨진다 (Databricks 트랙)**

OBO는 앱이 접속한 사람의 신분으로 데이터를 읽는 기능이고, 그래서 UC 행 필터·컬럼 마스킹이 그 사람 기준으로 적용된다. 프록시를 넣으면 Databricks 입장에서 접속자는 사용자가 아니라 **앱마켓**이다. 그러면 두 길뿐인데 둘 다 나쁘다.

- 마켓 대표 계정으로 접속 → 모든 사용자가 동일 권한. 문서가 예외 승인 대상으로 규정한 **SP 모드**가 된다
- 마켓이 사용자별 Databricks 토큰을 중계 → 전 임직원의 자격증명을 다루는 장치가 된다. 게다가 각 사용자가 어차피 Databricks SSO를 해야 하므로 리다이렉트와 다를 게 없다

즉 **프록시는 `AXM-0001`이 Databricks Apps를 택한 가장 큰 이유(Q5, UC 행·열 보안 자동 상속)를 스스로 무너뜨린다.**

**2. 온프렘 앱 트래픽이 AWS를 왕복한다 (Private Cloud 트랙)**

OBO 논거는 Databricks에만 적용되지만, VKS 트랙에는 별개의 더 나쁜 문제가 있다.

```
리다이렉트 — 사용자(온프렘) ──▶ VKS(온프렘)
             DX 통과 0회. 전부 사내망 안에서 끝난다

프록시    — 요청 왕복마다
             사용자(온프렘) ─DX─▶ 마켓(AWS) ─DX─▶ VKS(온프렘)
             사용자 ◀─DX─ 마켓(AWS) ◀─DX─────────┘
             DX 통과 4회
```

**온프렘 사용자가 온프렘 앱을 쓰는데 트래픽이 AWS를 왕복한다.** 지연이 늘고, 순수 사내 트래픽이 DX 대역폭을 잡아먹는다.

**3. 하필 가장 무거운 앱이 Private Cloud에 모인다**

`AXM-0005`로 재정의한 Q8·Q8′에 따라 **24×7 정지 불가 앱과 동시 사용자가 단일 인스턴스를 넘는 앱이 Private Cloud로 간다.** 프록시를 택하면 앱마켓을 그 앱들의 트래픽 합으로 사이징해야 한다. 정확히 최악의 조합이다.

**4. 트래픽량·장애 범위·구현 복잡도 (양쪽 공통)**

- 리다이렉트: 마켓은 카탈로그 조회·검색·실행 클릭만 처리한다. 임직원 1만 명이 하루 5회 열어도 5만 요청/일, 피크 수십 건/초 → **작은 인스턴스 2대**
- 프록시: 앱 사용 트래픽 전부. 동시 사용자 500명이면 수백~수천 건/초 + 연결 유지. **Databricks App 자체가 2 vCPU인데 그 앞의 프록시가 훨씬 커야 하는** 기이한 구조가 된다
- 마켓 장애 = 전 앱 정지. 앱마켓의 가용성 요구가 "모든 앱 중 최고"가 된다
- WebSocket·스트리밍·파일 업다운로드·리다이렉트 체인·쿠키 도메인. 게다가 Databricks Apps는 자체 OAuth를 강제하므로 프록시가 그 인증 흐름과 계속 싸워야 한다

### 실행 엔드포인트를 두는 이유

단순 리다이렉트(마켓이 실제 URL을 그대로 노출)가 아니라 마켓 소유 주소를 한 단계 두는 이유는 **런타임이 둘이고 앱이 그 사이를 이동하기 때문**이다.

- **런타임 이전 시 링크가 안 깨진다.** 비용 때문에 Databricks → Private Cloud로 가거나 데이터 요건 때문에 반대로 갈 수 있다. 실제 URL이 바뀌어도 사용자 북마크와 공유 링크는 유지된다
- **콜드 스타트를 처리할 자리가 생긴다.** `AXM-0005`의 유휴 정지 정책을 도입하면 정지된 앱을 클릭하는 일이 일상이 된다. "시작 중입니다" 화면이 여기 들어간다
- **실행 클릭이 마켓 로그에 남는다.** 리다이렉트의 계측 약점을 부분적으로 보완한다
- 실행 시점에 마켓이 권한을 한 번 더 확인한다 (최종 방어는 여전히 런타임)

**이것은 프록시가 아니다.** 최초 한 번만 관여하고 빠진다. 이후 화면 갱신·차트·클릭은 사용자와 런타임 직통이며, 마켓이 처리하는 것은 "실행 클릭 횟수"이지 "앱 사용량"이 아니다.

## 결과

**얻는 것**
- 앱마켓이 **저트래픽 서비스**로 남는다. ALB + 작은 인스턴스 2대(Multi-AZ) 수준
- OBO가 온전히 작동한다. 데이터 거버넌스 책임이 플랫폼에 남는다
- 온프렘 앱 트래픽이 사내망 안에서 끝난다
- 앱 하나가 느리거나 죽어도 마켓과 다른 앱은 영향받지 않는다
- 두 런타임이 사용자에게 **동일한 실행 경험**으로 보인다

**감수하는 것**
- **권한 회수 반영 지연.** 마켓에서 회수해도 런타임 그룹 동기화 주기만큼 시차가 생긴다(`03` §5-2). 즉시 차단 절차를 별도로 정의해야 한다
- **계측이 완전하지 않다.** 사용자가 실제 앱 URL을 북마크하면 실행 엔드포인트를 건너뛴다. 정확한 사용량은 `AXM-0008`의 조정 루프가 런타임에서 수집한다
- 화면 경험이 마켓과 앱으로 나뉜다. 새 탭 열기 + 스캐폴드 공통 헤더로 완화한다

## 검토한 대안

| 대안 | 평가 | 기각 사유 |
|---|---|---|
| 프록시 | 즉시 차단·정확한 계측 | 위 근거 1~4. 얻는 두 가지는 리다이렉트에서도 다른 방법으로 얻을 수 있다 |
| 하이브리드 (Private Cloud만 프록시) | 절충 | VKS야말로 헤어핀과 고트래픽 문제가 심한 쪽이다. 절충의 방향이 반대 |
| 단순 리다이렉트 (실제 URL 직접 노출) | 가장 단순 | 런타임 이전 시 링크가 깨지고, 콜드 스타트를 처리할 자리가 없다 |

## 미결 / 후속

- **즉시 차단 절차 정의** — 최종 수단은 앱 권한 회수가 아니라 **AD/SSO 계정 잠금**이다(어느 방식이든 즉시 작동하며 앱 단위 회수보다 강력). 여기에 마켓이 그룹 동기화를 기다리지 않고 `CAN_USE`를 직접 회수하도록 만들면 지연이 줄어든다. 보안팀 협의 항목
- 앱마켓 → Databricks 그룹 → `CAN_USE` 자동화 API 설계
- 실행 엔드포인트의 콜드 스타트 대기 UX — 콜드 스타트 실측이 선행되어야 한다(`04` §7-3)
- 런타임 이전 시 실제 URL 교체 절차 (`AXM-0008`의 조정 루프가 현재 런타임을 알고 있으므로 자동화 가능)
