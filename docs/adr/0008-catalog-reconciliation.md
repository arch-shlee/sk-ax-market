# AXM-0008: 카탈로그 등록 모델 — 조정 루프 기반

- **상태**: Proposed
- **일자**: 2026-09-12
- **결정자**: (승인 대기)
- **관련 문서**: `02` §9-2, `03` §6, `AXM-0005`, `AXM-0007`

## 맥락

`02` §9-2의 현재 설계는 **파이프라인이 배포 성공 시 마켓 API로 1회 POST**하는 push 모델이다.

```yaml
register:marketplace:
  stage: verify
  needs: [verify:databricks:prod]
  script:
    - curl -X POST "$APP_MARKET_API/apps/$APP_NAME/deployments" ...
```

Backstage 사례가 주는 교훈은 이 모델이 낡는다는 것이다. "Backstage 카탈로그는 정적 YAML로 구동되고 개발자가 수동으로 유지하도록 기대된다. 개발자는 메타데이터 유지를 싫어하고, **카탈로그는 빠르게 낡는다.**" 카탈로그 완전성 90% 이상인 조직은 예외 없이 자동 발견을 쓴다.

**우리 경우에는 이 문제가 더 심각하다.**

1. **Databricks Apps는 마켓 밖에서 상태가 바뀐다.** 워크스페이스 UI에서 앱을 정지·삭제할 수 있다. 마켓이 모르면 유령 항목이 남는다
2. **`AXM-0005`의 유휴 정지 정책을 도입하면 상태가 하루에도 여러 번 토글된다.** 1회 POST로는 절대 따라갈 수 없다

## 결정

> 파이프라인 POST는 진실이 아니라 **"이벤트 힌트"** 로 두고, 진실은 **엔티티 프로바이더 + 조정 루프**가 만든다.

| 프로바이더 | 권위 있는 소스 | 가져오는 것 |
|---|---|---|
| GitLab | 저장소 · 컴플라이언스 레이블 · 파이프라인 | 앱의 존재, 소유자, 증적, 승인 이력 |
| Databricks | 워크스페이스 Apps API · 시스템 테이블 | 실제 상태, 서빙 버전, 권한, 사용량, 비용 |
| VKS | Flux · K8s API | 실제 상태, 서빙 다이제스트 |

**결과적 일관성을 받아들이고, 고아(orphan) 처리 전략을 명시한다.**

## 근거

- Backstage의 검증된 구조를 그대로 차용한다 — 프로바이더가 권위 있는 외부 소스에서 데이터를 가져와 추가/삭제를 알리고, 처리 루프가 지속적으로 조정하며, 부모가 더 이상 자식을 방출하지 않으면 고아 전략이 작동한다
- **진실을 파이프라인이 만들면 파이프라인이 돌지 않는 동안의 변화를 놓친다.** 정지/삭제/권한 변경은 파이프라인 밖에서 일어난다
- 조정 루프는 `AXM-0005`의 유휴 정지 정책과 **같은 데이터를 반대 방향으로 쓴다.** 정지 스케줄러가 상태를 바꾸고 조정 루프가 그것을 읽는다

## 결과

**얻는 것**
- 카탈로그가 낡지 않는다. 유령 항목·유령 상태가 사라진다
- 앱마켓 없이 배포된 앱(수동 생성 등)도 발견된다 — **거버넌스 관점에서 이게 크다.** 섀도 앱 탐지가 부수 효과로 따라온다
- 파이프라인이 앱마켓 API에 강결합되지 않는다. 마켓이 잠시 죽어도 배포가 실패하지 않는다

**감수하는 것**
- **결과적 일관성.** 배포 직후 카탈로그에 즉시 반영되지 않을 수 있다. 이벤트 힌트로 지연을 줄이되 즉시성을 보장하지는 않는다
- 프로바이더별 폴링이 Databricks API·시스템 테이블에 부하와 비용을 만든다. 주기 설계 필요
- 고아 처리 전략을 잘못 잡으면 멀쩡한 항목이 사라지거나 죽은 항목이 남는다

## 검토한 대안

| 대안 | 평가 | 기각 사유 |
|---|---|---|
| 현행 push 1회 (`02` §9-2) | 단순, 즉시 반영 | 상태 변화를 따라가지 못한다. 유휴 정지 정책과 양립 불가 |
| 웹훅 (Databricks/GitLab → 마켓) | 지연 최소 | Databricks Apps 상태 변경 웹훅이 있는지 불확실. 있어도 유실 시 복구 수단이 필요하므로 조정 루프는 어차피 있어야 한다 |
| 카탈로그-as-code (저장소의 YAML 기술자) | Backstage 기본 | 개발자가 수동 유지 → 낡는다는 것이 바로 그 사례의 교훈. 런타임 상태는 애초에 표현 불가 |

## 미결 / 후속

- **고아 처리 전략 결정** — GitLab에서 저장소가 사라진 앱, Databricks에서 삭제된 앱을 지울지 보존할지. `03` §6의 `deprecation`과 여기서 만난다
- 프로바이더별 폴링 주기와 그 비용
- 조정 루프의 실행 위치 (앱 프로세스 내 스케줄러 vs 별도 워커) — 후자면 인프라 뷰에 박스가 하나 늘고 아웃바운드 경로가 명시되어야 한다
- 이벤트 힌트의 형태 (파이프라인 POST 유지 / 메시지 큐)
