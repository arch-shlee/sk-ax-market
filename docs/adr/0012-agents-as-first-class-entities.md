# AXM-0012: Databricks Agent를 마켓의 1급 엔티티로 편입하되 거버넌스 집행은 Unity Catalog에 위임한다

- **상태**: Proposed
- **일자**: 2026-09-12
- **결정자**: (승인 대기)
- **관련 문서**: `AXM-0007`, `AXM-0008`, `AXM-0009`, `AXM-0005`, `02` §8, `03` §6

## 맥락

기획서의 AX App 정의는 일반 Web App뿐 아니라 **Databricks Agent 연계 대화형·자동화 앱**을 포함한다. 그런데 지금까지의 설계는 **"에이전트를 쓰는 앱"만 다루고 에이전트 자체는 1급 엔티티가 아니다.** `02` §8에 Agent App 게이트가 있고 `03` §6에 `ai_bom` 필드가 있지만, 둘 다 앱의 속성으로 붙어 있다.

에이전트가 앱과 다른 지점은 **재사용된다는 것**이다. 하나의 에이전트를 여러 앱이 부품으로 쓰고, 에이전트가 다른 에이전트를 호출한다. 앱의 속성으로 표현하면 같은 에이전트가 여러 앱에 중복 기록되고 실제 인벤토리를 만들 수 없다.

Gartner는 포춘 500 기업이 2028년까지 평균 15만 개 이상의 에이전트를 쓰게 될 것으로 보면서 **중앙 인벤토리·에이전트 아이덴티티·권한·수명주기·지속 모니터링**을 권고한다. 반면 거버넌스가 준비됐다고 답한 조직은 13%에 그친다.

**동시에, Databricks가 이미 상당 부분을 제공한다.** 마켓이 이를 다시 만들면 중복이다.

## 결정

> 에이전트를 **마켓 레지스트리의 1급 엔티티**로 편입한다. 단, **권한 집행·데이터 통제·감사는 Unity Catalog에 위임**하고 마켓은 오케스트레이션과 발견 UI를 담당한다.

`AXM-0009`(리다이렉트)·`AXM-0011`(forward-auth)과 같은 원칙이다 — **마켓은 오케스트레이터, 플랫폼이 집행자.**

| 책임 | 주체 |
|---|---|
| 권한 집행, 데이터 접근 통제(OBO), 감사 로깅, 툴 호출 정책 | **Unity Catalog / Unity Gateway** |
| **임직원용 발견 UI** | **마켓** — Catalog Explorer는 데이터 담당자용이지 임직원용이 아니다 |
| **앱 + 에이전트 통합 뷰**, 의존 관계 표시 | **마켓** |
| 승인·증적 체인, AI-BOM, 판정 근거, 재평가 이력 | **마켓** |
| 권한 신청·부여 오케스트레이션 (실제 grant는 UC가 수행) | **마켓** |

**대상 경로는 오늘 동작하는 것으로 한정한다** — `deploy()`가 만드는 **UC 등록 모델 + Model Serving 엔드포인트**. Agent Services(UC에 agent service로 등록)는 GA 이후로 미룬다(§미결).

## 근거

- **에이전트는 UC securable이다.** `EXECUTE`(호출+발견) / `READ METADATA` / `MANAGE` 권한 체계를 그대로 쓴다. 마켓이 별도 권한 체계를 만들 이유가 없다
- **OBO가 종단 간 작동한다.** "사용자가 UC에서 접근하지 못하는 테이블은 그를 대신하는 에이전트도 접근하지 못한다." 공유 서비스 계정이 아니다. 앱의 OBO와 같은 원리이므로 `AXM-0001`의 Q5 논리가 에이전트에도 그대로 적용된다
- **감사가 이중 신원으로 남는다.** 실제 사용자와 에이전트 양쪽이 기록되고, 추론 테이블에 요청 페이로드가 남는다
- **에이전트는 워크스페이스 100개 한도에 걸리지 않는다.** UC 객체(계정 레벨)이므로 워크스페이스 분할 축 논의에서 제외된다
- 반대로 **발견은 Databricks가 해결하지 못한다.** Catalog Explorer는 데이터 담당자의 도구다. 전 임직원이 업무 에이전트를 찾는 자리가 아니다. 여기가 마켓의 자리다

## 결과

**얻는 것**
- 에이전트 중앙 인벤토리가 생긴다. `AXM-0008`의 조정 루프가 UC를 순회하므로 **마켓을 거치지 않고 만들어진 에이전트도 발견된다** — 섀도 에이전트 탐지
- 같은 에이전트를 쓰는 앱들을 관계로 표현할 수 있다. "이 에이전트를 고치면 어디가 영향받는가"에 답할 수 있다
- 권한 체계를 새로 만들지 않는다

**감수하는 것**
- **레지스트리 엔티티 모델이 커진다.** 종류(kind)와 관계가 필요하다 → `AXM-0007` 개정
- **"실행" 개념이 갈린다.** API로만 호출되는 에이전트는 `AXM-0009`의 실행 엔드포인트가 성립하지 않는다. 마켓은 실행 버튼 대신 **"어디에 쓰이는가"** 를 보여준다
- 권한 부여 대상이 트리가 된다 — 에이전트 `EXECUTE` + 툴(UC function, Genie space, vector index, MCP) 각각. 다만 데이터 권한은 OBO가 처리하므로 마켓의 책임 범위는 "호출 가능 여부"까지다
- **재평가 수명주기가 추가된다.** 기반 모델이 바뀌면 Agent Evaluation을 다시 돌려야 한다. 앱에는 없는 개념이다
- 비용 축이 하나 는다 (§`04` §2-3)

## 검토한 대안

| 대안 | 평가 | 기각 사유 |
|---|---|---|
| 에이전트를 앱의 속성(`ai_bom`)으로만 유지 (현행) | 단순 | 재사용되는 에이전트가 여러 앱에 중복 기록된다. 실제 인벤토리를 만들 수 없고 영향 범위를 못 구한다 |
| 마켓이 자체 권한 체계를 구축 | 통합 통제 | UC가 이미 하는 일이다. OBO를 깨뜨리게 되며 `AXM-0009`에서 프록시를 기각한 것과 같은 실수 |
| Agent Services(UC) 기반으로 지금 구현 | 장래 표준 | **beta이고 등록된 서비스를 통한 런타임 호출이 아직 미지원.** 지금 고정하면 위험 |
| 에이전트는 마켓 범위 밖으로 둔다 | 범위 축소 | 기획서의 AX App 정의에 이미 포함되어 있다. 그리고 발견 문제는 Databricks가 풀어주지 않는다 |

## 미결 / 후속

- **Agent Services GA 시점 확인.** GA되면 레지스트리 프로바이더를 UC agent service 기준으로 전환할지 재검토한다. 그때 이 ADR을 개정한다
- **Unity Gateway의 예산 한도**(사용자·그룹별 지출 임계)를 `AXM-0005`의 비용 통제 수단으로 채택할지
- 재평가 트리거 정의 — 기반 모델 변경 감지 방법과 재평가 실패 시 조치
- 에이전트의 "소유자"를 앱과 같은 방식으로 관리할지 (에이전트는 여러 조직이 공유할 수 있다)
- API로만 호출되는 에이전트의 사용량 계측 — 추론 테이블 기반
