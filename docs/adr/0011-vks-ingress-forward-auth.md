# AXM-0011: Private Cloud 트랙의 신원 주입은 Ingress forward-auth로

- **상태**: Proposed
- **일자**: 2026-09-12
- **결정자**: (승인 대기)
- **관련 문서**: `03` §5-2, `AXM-0009`, `databricks-apps-reference.md` §4-2

## 맥락

두 런타임 사이에 **비대칭**이 있다.

**Databricks Apps**는 플랫폼이 사용자 신원을 앱에 넣어준다. `x-forwarded-access-token` 헤더로 사용자 액세스 토큰이 전달되므로, 앱 개발자는 아무것도 하지 않아도 **검증된 신원이 도착한 상태**에서 시작한다.

**Private Cloud(VKS) 앱에는 그게 없다.** 각 앱이 알아서 Keycloak 연동을 구현해야 한다. 그러면 앱마다 품질이 갈리고, 이는 문서가 반복해서 **"검증으로 잡아내기 가장 어려운 유형의 위험"** 이라고 부른 지점이다. SAST·SCA·Secret 스캔으로 "이 앱이 인증을 제대로 했는가"를 판정할 수 없다.

`03` §5-2는 Private Cloud의 런타임 권한 부여를 "Keycloak RBAC + Ingress 인가 정책"으로 적어 두었으나, **그 Ingress 정책이 구체적으로 무엇인지는 정의되지 않았다.**

`AXM-0009`를 검토하는 과정에서 "그렇다면 앱마켓이 앞에 서서 인증하면 어떤가"라는 안이 나왔으나, 그것은 프록시 방식이고 별도의 더 큰 문제를 만든다(동 문서 근거 2~4).

## 결정

> VKS Ingress에 **identity-aware proxy(forward-auth)** 를 두어, **플랫폼이 검증된 신원을 헤더로 주입**한다. 앱마켓은 트래픽 경로에 두지 않는다.

Keycloak 연동 forward-auth(oauth2-proxy 계열)를 Ingress 레벨에 배치하고, 인증되지 않은 요청은 앱에 도달하기 전에 차단한다.

**결과적으로 두 트랙이 대칭이 된다.**

| | Databricks Apps | Private Cloud (VKS) |
|---|---|---|
| 인증 주체 | Databricks 플랫폼 | **Ingress forward-auth** |
| 앱이 받는 신원 | `x-forwarded-access-token` | `X-Forwarded-User` / OIDC 토큰 헤더 |
| 앱 코드가 할 일 | 헤더 읽고 UC 조회 | 헤더 읽고 인가 판단 |
| 행·열 데이터 통제 | **UC가 자동** | **앱 코드** ← 격차 잔존 |

## 근거

- **인증 구현을 앱에서 플랫폼으로 옮긴다.** `02` §1의 설계 원칙 "강제는 플랫폼이, 작성은 개발자가 하지 않는다"가 보안 스캔뿐 아니라 인증에도 적용되어야 한다
- 앱 개발자에게 **"어느 런타임이든 헤더에 검증된 사용자가 온다"** 는 단일 계약을 줄 수 있다. Golden Path 스캐폴드가 두 트랙에서 같은 코드를 쓸 수 있게 된다
- 스캐너로 판정하기 어려운 항목을 **아키텍처로 제거**한다. 앱이 인증을 구현하지 않으므로 잘못 구현할 수도 없다
- 앱마켓을 경로에 두는 안(프록시)보다 낫다 — 헤어핀 라우팅이 없고, 앱마켓 장애가 앱 접근에 영향을 주지 않는다

## 결과

**얻는 것**
- 두 트랙의 인증 품질이 균일해진다
- 앱 코드에서 인증 로직이 사라진다. 스캐폴드가 단순해진다
- 검증 게이트에서 "인증 구현 검토" 항목을 제거할 수 있다

**감수하는 것**
- **행·열 수준 데이터 통제의 격차는 여전히 남는다.** forward-auth는 "누구인가"를 보장하지만 "그 사람이 어느 행을 볼 수 있는가"는 앱 코드 책임이다. **이것이 Q5가 Databricks를 선호하는 이유이며, 이 ADR로 해소되지 않는다**
- Ingress에 인증 구성요소가 추가되어 VKS 플랫폼의 운영 대상이 하나 늘어난다
- 헤더 신뢰 경계를 명확히 해야 한다. 앱이 외부에서 온 `X-Forwarded-User`를 그대로 믿으면 위조 가능하므로, **Ingress가 해당 헤더를 항상 덮어쓰도록** 구성해야 한다

## 검토한 대안

| 대안 | 평가 | 기각 사유 |
|---|---|---|
| 각 앱이 Keycloak 연동을 직접 구현 (현행 암묵) | 자유도 | 앱마다 품질이 갈리고 검증으로 잡을 수 없다. 문서가 지적한 최대 위험 유형 |
| 앱마켓이 프록시로 앞에 선다 | 중앙 통제 | `AXM-0009` 근거 2~4 — 헤어핀 라우팅, 고트래픽 앱 집중, 장애 범위 |
| 서비스 메시(mTLS + 인가 정책) | 세밀한 통제 | 사용자 인증이 아니라 서비스 간 인증 수단이다. 목적이 다르고 도입 비용이 크다 |
| 스캐폴드에 인증 라이브러리 기본 탑재 | 구현 부담 경감 | 개발자가 제거·수정할 수 있으므로 강제가 아니다. `02` §1 원칙에 어긋난다 |

## 미결 / 후속

- forward-auth 구현체 선정 (oauth2-proxy / Keycloak gatekeeper / Ingress 컨트롤러 내장 기능)
- **헤더 덮어쓰기 구성 검증** — 위조 방지의 핵심
- 앱에 전달할 신원 정보의 범위 (사용자 ID, AD 그룹, 조직 코드). `03` §5-2의 "앱 내부 세분 역할" 처리와 맞물린다
- 행·열 통제 격차를 Private Cloud에서 어떻게 다룰지 — 앱 코드 책임으로 남길지, 공통 데이터 접근 계층을 둘지. **별도 ADR 후보**
