# AXM-0001: 운영 런타임 2종 채택과 Databricks Apps 우선 적용

- **상태**: Accepted
- **일자**: 2026-09-12 (원 결정은 기획서 `AX앱마켓구성1.pdf`)
- **결정자**: 기획 (AX)
- **관련 문서**: `03-runtime-decision-and-architecture.md`, `AXM-0004`, `AXM-0005`

## 맥락

AX App은 어디에서 실행될 것인가. 기획서는 두 개의 운영 Runtime을 두고, 1안으로 Databricks Apps를 우선 적용한다고 정했다. 다만 기획서 자신이 **"이거는 좀더 배경과 명분을 강화해야 할 필요는 있다"** 고 적어 두었다.

## 결정

> 운영 런타임을 **Databricks Apps**와 **Private Cloud(VKS)** 2종으로 두고, **단계적으로 Databricks Apps를 먼저 적용**한다.

앱마다 어느 런타임에 배치할지는 판정 트리(`03` §2)로 결정한다. 기획서의 "Databricks 내 데이터가 필요한 경우"라는 기준은 실무에서 갈리지 않으므로 — 업무앱 대부분이 데이터를 필요로 하고 Databricks 데이터는 SQL Warehouse·JDBC로 Private Cloud에서도 접근 가능하다 — 판정을 3층(차단 조건 / 강한 선호 / 기본값)으로 분리한다.

## 근거

- **Private Cloud는 기구축**이므로 커스텀 런타임·특수 언어·고가용성 요구를 흡수할 수 있다
- **Databricks Apps는 UC 행 필터·컬럼 마스킹을 OBO로 자동 상속**한다. Private Cloud에서 동등 통제를 구현하려면 앱 코드가 책임져야 하고, 이는 검증으로 잡아내기 가장 어려운 유형의 위험이다
- 1안을 Databricks Apps로 두면 별도 인프라 구축 없이 시작할 수 있다

## 결과

**얻는 것**
- 앱 특성에 맞는 배치가 가능하다
- 데이터 거버넌스 책임을 앱 코드에서 플랫폼으로 옮길 수 있는 경로가 생긴다

**감수하는 것**
- **두 트랙의 파이프라인·증적·지표를 각각 설계해야 한다.** "공통 검증 기준"의 실질은 도구 통일이 아니라 증적 등급의 동등성이다(`02` §1)
- 운영 지표·비용의 **정규화 계층**이 필요하다. 단위가 다르다(DBU/시간 vs 자원 점유)
- Databricks Apps는 앱 수에 비례해 비용이 선형 증가한다 → `AXM-0005`

## 검토한 대안

| 대안 | 평가 | 기각 사유 |
|---|---|---|
| Private Cloud 단일 런타임 | 비용은 최소 | UC 행·열 보안 상속을 포기하게 된다. Agent·Genie 연계 앱의 이점도 사라짐 |
| Databricks Apps 단일 런타임 | 운영 단순 | 커스텀 런타임·지원 외 언어·고가용성 요구를 수용할 수 없다. 앱 100개 한도 |

## 미결 / 후속

- **3층 기본값은 조건부다.** 유휴 정지 정책과 공용 웨어하우스 규칙이 구현된 동안에만 Databricks Apps를 기본값으로 한다 → `AXM-0005`
- 판정 트리에 **데이터 등급 축이 없다**. A5 확정 후 추가 필요 (`05` §8-1)
